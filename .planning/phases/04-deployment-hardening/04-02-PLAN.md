    Install Sentry:
    ```
    npm install @sentry/nextjs
    ```
    Do NOT run the Sentry wizard (npx @sentry/wizard) — it overwrites files and prompts interactively. Create config files manually instead.

    Create `sentry.client.config.ts`:
    ```ts
    import * as Sentry from "@sentry/nextjs";

    Sentry.init({
      dsn: process.env.SENTRY_DSN,
      environment: process.env.NODE_ENV || "development",
      tracesSampleRate: process.env.NODE_ENV === "production" ? 0.2 : 1.0,
      replaysSessionSampleRate: 0.1,
      replaysOnErrorSampleRate: 1.0,
      integrations: [Sentry.replayIntegration()],
    });
    ```

    Create `sentry.server.config.ts`:
    ```ts
    import * as Sentry from "@sentry/nextjs";

    Sentry.init({
      dsn: process.env.SENTRY_DSN,
      environment: process.env.NODE_ENV || "development",
      tracesSampleRate: process.env.NODE_ENV === "production" ? 0.2 : 1.0,
    });
    ```

    Create `sentry.edge.config.ts`:
    ```ts
    import * as Sentry from "@sentry/nextjs";

    Sentry.init({
      dsn: process.env.SENTRY_DSN,
      environment: process.env.NODE_ENV || "development",
      tracesSampleRate: process.env.NODE_ENV === "production" ? 0.2 : 1.0,
    });
    ```

    Create `instrumentation.ts` at project root:
    ```ts
    export async function register() {
      if (process.env.NEXT_RUNTIME === "nodejs") {
        await import("./sentry.server.config");
      }
    }
    ```
    This hooks into Next.js instrumentation lifecycle to initialize Sentry on server start.

    Update `next.config.ts`:
    ```ts
    import { withSentryConfig } from "@sentry/nextjs";
    import type { NextConfig } from "next";

    const nextConfig: NextConfig = {
      output: "standalone",
    };

    export default withSentryConfig(nextConfig, {
      org: process.env.SENTRY_ORG,
      project: process.env.SENTRY_PROJECT,
      silent: !process.env.CI,
      widenClientFileUpload: true,
      hideSourceMaps: true,
      disableLogger: true,
      tunnelRoute: "/monitoring",
    });
    ```
    The `tunnelRoute: "/monitoring"` creates a server-side proxy for Sentry events so client-side errors reach Sentry even when ad-blockers block sentry.io.

    ```
    SENTRY_DSN=
    SENTRY_ORG=
    SENTRY_PROJECT=
    ```

<task type="auto">
  <name>Task 2: Add Sentry error boundary and verify integration</name>

    Create `app/global-error.tsx` (root error boundary with Sentry):
    ```tsx
    "use client";

    import * as Sentry from "@sentry/nextjs";
    import { useEffect } from "react";

    export default function GlobalError({
      error,
      reset,
    }: {
      error: Error & { digest?: string };
      reset: () => void;
    }) {
      useEffect(() => {
        Sentry.captureException(error);
      }, [error]);

      return (
        <html>
          <body>
            <div style={{
              display: "flex", flexDirection: "column",
              alignItems: "center", justifyContent: "center",
              minHeight: "100vh", fontFamily: "system-ui, sans-serif",
              padding: "2rem", textAlign: "center"
            }}>
              <h1 style={{ fontSize: "2rem", marginBottom: "1rem" }}>
                Er is iets misgegaan
              </h1>
              <p style={{ marginBottom: "2rem", color: "#666" }}>
                Er is een onverwachte fout opgetreden. Ons team is op de hoogte gesteld.
              </p>
              <button
                onClick={() => reset()}
                style={{
                  padding: "0.75rem 1.5rem",
                  background: "var(--accent, #0052cc)",
                  color: "#fff",
                  border: "none",
                  borderRadius: "6px",
                  cursor: "pointer",
                  fontSize: "1rem",
                }}
              >
                Opnieuw proberen
              </button>
            </div>
          </body>
        </html>
      );
    }
    ```
    Note: `global-error.tsx` requires `<html>` and `<body>` tags since it replaces the root layout entirely (Next.js requirement).

    Do NOT modify the existing `app/error.tsx` — the existing file handles per-route errors with a lighter UI. `global-error.tsx` is only reached for root-level crashes.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → Sentry | Client-side error reports sent to sentry.io |
| Server → Sentry | Server-side error reports sent to sentry.io |
| Browser → /monitoring | Sentry tunnel route (avoids ad-blockers) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-03 | Information Disclosure | Sentry event payload | medium | mitigate | Source maps are uploaded to Sentry (not public). `hideSourceMaps: true` prevents non-Sentry access. Error payloads may contain request URLs but not auth tokens or passwords — the Sentry SDK automatically scrubs common PII fields. |
| T-04-04 | Information Disclosure | tunnelRoute: /monitoring | low | accept | The tunnel route is a thin proxy to sentry.io. It does not log or store event data. Rate-limited by Sentry's ingress. |
| T-04-05 | Tampering | sentry.client.config.ts | low | mitigate | DSN is read from env var (SENTRY_DSN), never hardcoded. GitHub secrets or Coolify env vars control the value. |
| T-04-SC | Tampering | npm install @sentry/nextjs | high | mitigate | Package from npm registry. Package-lock.json pins transitive deps. |
</threat_model>
