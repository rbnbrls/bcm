# Client Configuration — 3NF Architecture

## 1. Goal

Replace the flat client-configuration Excel dump with a fully normalised
PostgreSQL model in **Third Normal Form (3NF)**.  All configuration changes
must flow through the existing BCM change-management workflow; direct DML
against configuration tables is prohibited by database-level triggers.

## 3. 3NF Design

- Every non-primary-key attribute is fully functionally dependent on the PK.
- Lookup domains (asset class, sub-asset class, manager, benchmark,
  NPC classification) are separate tables with natural/business-key candidates
  explicitly UNIQUE-constrained.
- `portfolio_configuration` is a fact/configuration table referencing those
  lookups; it contains no repeating groups or transitive dependencies.
- History is preserved via a Slowly Changing Dimension Type 2 (SCD2) pattern:
  updates close the current row (active_ind=false) and insert a new active row.

### Business key generation

```
primary_account_id =
  {client_code}*{asset_class_code}{sub_asset_class_code}*{manager_code}
```

Example: `ADP*FIHYG*ROB`

Generated by `generatePrimaryAccountId()` in `lib/portfolio-config.ts` (and
re-derived by `buildPrimaryAccountId()` in `lib/validation-rules.ts` at apply
time); the `*`-separated shape is enforced by the column CHECK constraint
`^[A-Z0-9]{1,3}[*][A-Z]{2}[A-Z]{3}[*][A-Z0-9]{3}$`.

## 4. Schema Overview

All tables live under the `client_config` schema:

| Table | Purpose | Key columns |
|-------|---------|-------------|
| `portfolio` | Portfolio metadata | portfolio_code, parent_account_id |
| `asset_class` | Asset class lookup | asset_class_code, asset_class_name |
| `sub_asset_class` | Sub-asset class (FK→asset_class) | sub_asset_class_code, asset_class_id |
| `manager` | Manager lookup | manager_code, manager_name |
| `benchmark` | Benchmark catalog | benchmark_code, benchmark_name, rimes_code |
| `npc_classification` | NPC classification | classification_name |
| `portfolio_configuration` | Live configuration (SCD2) | primary_account_id + FK dimensions |
| `change_portfolio_configuration` | Staged change requests | change_request_id FK, action_type, target_primary_account_id (#331) |
| `change_lookup_request` | Staged lookup additions (new asset class / sub asset class / benchmark) | change_request_id FK, dimension, apply_status |
| `change_portfolio_metadata_request` | Staged portfolio / parent_account create+retire for existing clients (landed #315; **only in migrate.mjs, not canonical schema — G9**) | change_request_id FK, dimension, action_type (CREATE/RETIRE), code |
| `client_onboarding_staging` | Staged onboarding for genuinely new clients (client + initial portfolio metadata) | change_request_id FK (UNIQUE), client_code, status |

The onboarding staging table is the entry point for new pension funds that have
no `client_config.client` row yet. Its values do NOT need to exist in the live
tables — the apply step (stage → approve → apply) introduces them together in
one transaction. Idempotency is enforced by `UNIQUE (client_code, status)`.
See [client_onboarding_staging](database/data-model/client-onboarding-staging.md)
for the full column contract.

Legacy tables (same schema, pre-3NF):
- `account` — flat account records with FK references to the dimension tables
- `legal_entity`, `parent_account`, `model`, `classification`, `strategy`, `sub_strategy`

## 5. Business Rules

### Validation Rules (lib/validation-rules.ts)

| Field | Rule |
|-------|------|
| `portfolio_code` | Required, 2–15 chars, `^[A-Z0-9]{2,15}$` |
| `asset_class_code` | Required, exactly 2 uppercase letters |
| `sub_asset_class_code` | Required, 1–3 chars, linked to asset_class |
| `manager_code` | Required, 3 alphanumeric uppercase |
| `benchmark_code` | Required, 1–60 chars |
| `primary_account_id` | Pattern: `{client_code}*{AC}{subAC}*{manager}` (see §3) |
| `long_name` | Required, 1–255 chars, no CR/LF |
| `short_name` | Required, 1–100 chars, no CR/LF |
| `effective_from` | Required, ISO date |
| `effective_until` | Optional, must be ≥ effective_from |
| `rimes_code` | Required, **except** when `benchmark_code = 'DUMMY'` |

### Change-Management Enforcement (db/enforce_change_process.sql)

Three database triggers on `client_config.portfolio_configuration`:

- `trg_enforce_change_process_insert` (BEFORE INSERT)
- `trg_enforce_change_process_update` (BEFORE UPDATE)
- `trg_enforce_change_process_delete` (BEFORE DELETE)

All three raise an exception unless the session-level GUC
`app.change_process_bypass` is set to `'true'`. This GUC is only set by
`applyChangePortfolioConfigurations()` in `lib/client-config-db.ts`.

Direct SQL mutation of portfolio_configuration is **blocked** at the database
level with a Dutch-language error message guiding users to the BCM Change
process.

## 6. Change Process

```
1. User submits a change request via /changes/new
2. Frontend stages the change in change_portfolio_configuration
   (action_type: CREATE / UPDATE / DELETE)
3. Stakeholders review and approve
4. Status transitions to 'processed'
5. processChangeForProcessedStatus() is called (lib/change-processor.ts)
6. applyChangePortfolioConfigurations() is invoked (lib/client-config-db.ts):
   - Sets app.change_process_bypass = 'true'
   - For CREATE: INSERT new row (active_ind=true)
   - For UPDATE: close old row (active_ind=false), INSERT new row
   - For DELETE: set active_ind=false
7. Audit trail via audit_log / change_request history
```

`processChangeForProcessedStatus()` dispatches in order: (1) staged
`change_portfolio_metadata_request` rows (portfolio / parent_account
create/retire — landed #315), (2) staged `change_portfolio_configuration` rows
(portfolio configuration CREATE/UPDATE/DELETE), (3) legacy `portfolio_addition`
flat path, (4) IST-sync fallback for other change types. There is no
`customer_onboarding` branch yet (gap G1).

## 7. Migration Strategy

Migration from legacy flat data to the 3NF model uses
`lib/client-config-migration.ts`:

1. **Extract** legacy rows (from `client_config.account` or JSON import)
2. **Validate & enrich** each row:
   - Look up dimension codes (asset_class, sub_asset_class, manager, benchmark, NPC)
   - Build canonical primary_account_id
   - Validate field lengths, formats, date ranges
3. **Deduplicate** by canonical primary_account_id
4. **Insert** via the change-process bypass (same mechanism as applyChangePortfolioConfigurations)
5. **Rollback contract** is generated: maps original IDs to canonical IDs for reversal

Migration modes:
- **Dry-run**: validate without inserting (returns all errors/warnings + preview)
- **Live**: perform the insert (requires the GUC bypass)

## 8. Rollback Strategy

- Drop the three new tables (`portfolio_configuration`, `change_portfolio_configuration`,
  `npc_classification`) and their indexes.
- Revert application code to the previous schema-bound entities.
- The `account` table (legacy flat model) remains available until full cutover.
- If `portfolio_configuration` was populated via the migration service, the
  rollback contract provides exact DELETE statements to reverse the migration.

## 10. Dimension Classification: ADMIN-ONLY vs USER-REQUESTABLE

Every `client_config` lookup dimension is classified to determine whether a
user can request a new value through the governed change workflow or whether
the value set is admin-maintained master data.

| Dimension | Classification | Justification |
|-----------|---------------|---------------|
| `manager` | **ADMIN-ONLY** | FK-enforced `manager_code` is part of `primary_account_id` account identity. External counterparty codes set by operations. User creation not desired. |
| `npc_classification` | **ADMIN-ONLY** | FK-enforced internal labeling taxonomy (e.g. "Geen NPC"). Not client-facing; no user creation path exists. |
| `benchmark` | **USER-REQUESTABLE** | User-driven investment decisions. Dedicated `/benchmark-aanvraag` change flow and `__NEW__` inline option already exist. Deliberately **no FK** so staged rows can reference a benchmark being requested in the same change. |
| `asset_class` | **USER-REQUESTABLE** | Client-supplied investment taxonomy. New asset classes are structural, high-impact events that should flow through the reviewable change process. |
| `sub_asset_class` | **USER-REQUESTABLE** | Always belongs to an asset class. Requested together with its parent through the same change flow. |

| Layer | Enforcement | Mechanism |
|-------|-------------|-----------|
| DB triggers | `portfolio_configuration` DML | `app.change_process_bypass` GUC (enforce\_change\_process.sql) |

## 11. Why direct writes to live client config are not allowed

Live `client_config` rows are the **source of truth for account mandates** — a
single row in `portfolio_configuration` is one mandate line for a pension fund,
and the full row set is the auditable configuration of the fund. Allowing ad-hoc
direct writes would break every invariant this architecture is built on:

1. **Single-writer enforcement (staged backend design).** Every lifecycle action
   goes through the BCM change workflow: a user *stages* an intent
   (`change_portfolio_configuration`, `change_lookup_request`,
   `client_onboarding_staging`), the change request is reviewed and approved,
   and only at status `processed` does the apply step mutate the live tables.
   The staged rows are the *proposal*; the live tables are the *committed
   state*. There is deliberately no "edit live row" path — the stage table
   *is* the edit path, and it is immutable once submitted.
2. **DB-level enforcement.** `trg_enforce_change_process_{insert,update,delete}`
   on `portfolio_configuration` (`db/enforce_change_process.sql`) raise an
   exception on any DML unless the session GUC `app.change_process_bypass` is
   set to `'true'`. The GUC is set **only** inside the apply functions
   (`applyChangePortfolioConfigurations()`, `applyChangeLookupRequests()`,
   `applyNewBenchmarkRequest()` in `lib/client-config-db.ts`), scoped to the
   apply transaction via `SET LOCAL`. Direct SQL from a console or an
   ungoverned code path is blocked with a Dutch error message pointing to the
   change process.
3. **SCD2 history is the audit trail.** UPDATE closes the current active row
   (`active_ind=false`, `effective_until` = change effective date) and inserts
   a new active row; DELETE soft-retires (`active_ind=false`). `active_ind` and
   `effective_until` are **system-managed** — a direct write would corrupt the
   history chain and break `WHERE active_ind = true` reporting (the exact
   filter `/admin/client-config` reads).
4. **Lineage.** Every live row carries `change_request_id` (UNIQUE FK →
   `change_requests(id)`, set by the apply path). A reviewer can trace any row
   to the change request that created it. Direct writes have no lineage.
5. **Validation happens before staging, re-validation at apply.** Form-level
   validation (`validatePortfolioAgainstReferenceData` in
   `app/changes/new/portfolio-actions.ts`) checks dimension existence and the
   admin-only boundaries; the apply path re-derives `primary_account_id` from
   the dimension codes and double-checks it. A direct write bypasses both
   gates.
6. **Admin-only dimensions stay admin-only.** `manager` and
   `npc_classification` values are operational master data with no user-facing
   creation path (missing value → "contact support / beheerder" error). The
   staged design makes that boundary structural: no staging table exists for
   these dimensions, so a change request cannot even express them.

**Corollary:** the *only* legitimate mutations of live client config are (a)
the apply functions inside the change processor, and (b) admin master-data
maintenance via `/admin/attribute-options` (itself a documented gap — see G5).
Everything else is a violation of the architecture.

## 12. Change-request taxonomy (target state)

Eight change request types across three lifecycle domains. Each type replaces a
direct write; the *only* "no type" rows are deliberate admin-only dimensions
(no user flow by design) and legacy out-of-scope types.

| ID | Slug / action | Domain | Staging | Apply | Replaces direct write? |
|----|---------------|--------|---------|-------|------------------------|
| **CR-OB-01** | `customer_onboarding` | Client onboarding | `client_onboarding_staging` (DDL merged #318; staging helpers merged #315; wizard UI merged #320) | **not yet wired into `processChangeForProcessedStatus` — G1.** Wizard stages via `saveClientOnboardingStaging()`; the apply-on-processed step (create client → parent_account + portfolio → initial `portfolio_configuration` rows, one transaction) is planned (t_2ef66742 / t_0c57ad94) | **YES** — replaces INSERT into `client`/`portfolio`/`parent_account`/`portfolio_configuration` |
| **CR-OB-02** | onboarding metadata correction (planned) | Client onboarding | reuse `client_onboarding_staging` or CR-PC-02 rows (TBD) | none yet — **GAP G2** | **YES** (by definition) |
| **CR-PC-01** | `portfolio_configuration` CREATE | Portfolio configuration | `change_portfolio_configuration` (action=`CREATE`) | `applyChangePortfolioConfigurations()` — INSERT active row | **YES** — trigger-blocked |
| **CR-PC-02** | `portfolio_configuration` UPDATE | Portfolio configuration | `change_portfolio_configuration` (action=`UPDATE`) | SCD2: close current row, INSERT new active row | **YES** — trigger-blocked |
| **CR-PC-03** | `portfolio_configuration` RETIRE (= DELETE) | Portfolio configuration | `change_portfolio_configuration` (action=`DELETE`) | soft retire: `active_ind=false`, `effective_until` = staged or today | **YES** — trigger-blocked |
| **CR-RD-01** | `new_asset_class` | Reference data | `change_lookup_request` (dimension=`asset_class`) | `applyChangeLookupRequests()` — INSERT into `asset_class` | **YES** (user flows; admin direct maintenance remains) |
| **CR-RD-02** | `new_sub_asset_class` | Reference data | `change_lookup_request` (dimension=`sub_asset_class`) | `applyChangeLookupRequests()` — INSERT into `sub_asset_class` | **YES** (user flows) |
| **CR-RD-03** | `new_benchmark` | Reference data | `change_lookup_request` (dimension=`benchmark`) **and** legacy `new_benchmark_requests` | `applyChangeLookupRequests()` / `applyNewBenchmarkRequest()` — INSERT into `benchmark` | **YES** (user flows) |
| **CR-RD-04** | `benchmark_switch` | Legacy (public schema, IST-sync) | legacy | `istSyncOnProcessed()` | **No** — out of `client_config` scope; consolidation candidate (G8) |

**Non-types (deliberate):** `manager` and `npc_classification` are **admin-only**
dimensions — no change request type exists and none should (see §11.6 and
`documentation/admin-only-dimensions.md`). Legacy generic types
(`fee_change`, `mandate_change`, `custodian_change`, `rebalance_trigger`) are
out of the client-config taxonomy.

**Portfolio / parent_account metadata (landed #315).** A companion staging
table `change_portfolio_metadata_request` (dimension `portfolio` |
`parent_account`, action CREATE | RETIRE) and
`stagePortfolioMetadataChange()` / `applyChangePortfolioMetadataRequests()`
now cover portfolio and parent_account **create/retire** for existing clients;
the processor runs it as step 1 (before portfolio-configuration apply).
UPDATE for these dimensions is **not** implemented (gap G2); the table exists
only in `scripts/migrate.mjs`, not yet in the canonical
`db/clientconfig_schema.sql` (schema drift — see §15 G9).

## 13. Field → change-flow coverage matrix (columns of `/admin/client-config`)

Ground truth: `app/admin/client-config/page.tsx` →
`getClientConfigPortfolioConfigurations()` (`lib/client-config-db.ts`) → single
SELECT on `portfolio_configuration pc` joined with `client`, `portfolio`,
`parent_account` (LEFT), `asset_class`, `sub_asset_class`, `manager`,
`benchmark`, `npc_classification`; rendered by
`app/admin/client-config/client-config-table.tsx` (`COLUMNS` array +
`formatCell`). Filter: `WHERE pc.active_ind = true`.

**Legend:** *direct* = stored on `portfolio_configuration` (or the referenced
code/id column); *derived* = computed (`buildPrimaryAccountId`), never
user-supplied; *joined* = label resolved from a lookup table via the FK stored
on the row; *system-managed* = written only by the apply path / DB.

## 14. Dependency graph of lifecycle issues

```
CR-OB-01 customer_onboarding
   │  D1: must reach 'processed' before any per-client flow (client_code FK)
   ├──► CR-PC-01 CREATE            (client + portfolio + lookups must exist)
   │        │  D2: row must exist (active)
   │        ├──► CR-PC-02 UPDATE
   │        └──► CR-PC-03 RETIRE
   └──► CR-RD-01 new_asset_class
            │  D4: parent must exist (same change or earlier)
            └──► CR-RD-02 new_sub_asset_class
CR-RD-03 new_benchmark   (D5: no staging dependency; lookup apply must run before
                          CR-PC apply within the same change)
```

| # | Dependency | Rule |
|---|------------|------|
| D1 | Onboarding → everything else | `portfolio_configuration.client_code` FK → `client`. No per-client flow before onboarding is `processed`. One client = one onboarding. |
| D2 | CREATE → UPDATE/RETIRE | UPDATE/RETIRE target an existing **active** row; staged UPDATE/DELETE with no matching active row fails at apply (verified in `applyChangePortfolioConfigurations`). |
| D3 | Portfolio metadata → accounts | `portfolio_configuration.portfolio_code` FK → `portfolio`. Portfolio rows are created by CR-OB-01 or the legacy `portfolio_addition` path; a governed portfolio/parent_account CREATE/RETIRE flow for existing clients now exists (`change_portfolio_metadata_request`, landed #315). Portfolio **UPDATE** and onboarding **corrections** remain gaps (G2). |
| D4 | asset_class → sub_asset_class | `sub_asset_class.asset_class_id` FK. CR-RD-02 requires the parent code to exist — staged atomically with CR-RD-01 when both are new. |
| D5 | Lookup apply → portfolio apply | Within one change, lookup rows (CR-RD-*) apply **before** portfolio rows (CR-PC-*) that reference them. Only `benchmark` can actually collide (no FK, same-change reference allowed); the processor must run `applyChangeLookupRequests`/`applyNewBenchmarkRequest` before `applyChangePortfolioConfigurations` when both are present. |
| D6 | Admin-only dimensions | No change flow; CR-PC-01/02 referencing a missing `manager`/`npc_classification` is rejected at **form validation** — the prerequisite is an admin action outside the taxonomy. |
