# Schema

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | `text` | `PRIMARY KEY` | Approval entry identifier (text — generated by application). |
| `change_request_id` | `uuid` | `NOT NULL, REFERENCES change_requests(id) ON DELETE CASCADE` | The change request being approved/rejected. |
| `approver` | `text` | `NOT NULL` | Name or identifier of the approver. |
| `decision` | `text` | `NOT NULL` | Approval decision. |
| `remarks` | `text` | | Optional remarks from the approver. |
| `created_at` | `timestamptz` | `NOT NULL, DEFAULT now()` | Record creation timestamp. |

# Constraints

- `chk_app_decision` — Decision must be either `approved` or `rejected`.

# Relationships

- Many-to-one with [change_requests](change-requests.md) via `change_request_id` (cascading delete)

# Indexes

| Index | Columns | Purpose |
|-------|---------|---------|
| `idx_app_change_request_id` | `change_request_id` | FK: approvals by change request |

# Usage

Approvals are part of the change request workflow. Depending on the change type's workflow configuration, a change request may require one or more approvals before it can proceed to `in_progress` or `processed` status.
